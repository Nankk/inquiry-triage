## Context

pipeline-skeleton の D7「エージェントの追加は 1 ファイル」と「導入はシャドーモードで」のうち、後者を実装する。
既存の経路（分類 → 表引き → 担当 → レビュー ∥ 検証 → キュー）には手を入れず、横に「記録だけの経路」を足す形にする。

## Decisions

### S1. 影にする単位は「カテゴリ → 影のエージェント名」の対応表
- 設定ファイル（JSON、標準ライブラリで読める）に `{"billing": "billing_specialist_v2"}` のように書く。1 行足せば影が走る。
- エージェントの定義（名前 → 人格）は agents.py の一覧に置き、本番の対応表と影の対応表はどちらもその一覧を参照する。昇格は本番の対応表の名前を書き換えるだけ。
- 代替案: CLI フラグ `--shadow billing=...`。却下理由: 運用で毎回打つものではなく、設定として残したい。
- 代替案: エージェント定義ごと設定ファイルに書く。却下理由: 人格文（プロンプト）はコードの一部としてレビューとテストの対象にしたい。

### S2. 影に渡す入力は既存と同じ
- 同じ問い合わせ、同じ候補記事（表引きは 1 回だけ）。比較が成り立つのは入力が同じときだけ。
- 影の fixture キーも `<影のエージェント名>/<inquiry_id>.json`。リプレイの仕組みはそのまま使える。

### S3. 影にも既存と同じ 2 系統の検査（LLM レビュー ∥ 決定論的検証）を付ける
- 比較指標はレビュー判定（pass / flag と理由）と警告数の両方。
- 経緯（2026-11-08）: Claude Code の起草案は「決定論的検証のみ、指標は警告数、LLM レビューはコスト倍増を避けて付けない」だった。作者のレビューで却下。理由: シャドーモードが要る時点は、安定した v1 があって機能を積極的に良くしたい段階であり、「警告数を 0 に近づける」という開発段階のマイナス削減の指標では改良の良し悪しを判定できない。規程への適合や顧客への配慮といった LLM にしか判定できない観点を比較に含めるには、影にもレビューの呼び出しが要る。
- 代替案（却下）: 決定論的検証のみ。コストは半分で済むが、上記のとおり比較の目的に合わない。コストは影を対象カテゴリに限ることで抑える。
- 影のレビューの fixture キーは `reviewer/<inquiry_id>.shadow.json`。既存のレビュー（`reviewer/<inquiry_id>.json`）と同じ問い合わせ ID で衝突するため、業務キーに「.shadow」を足して区別する。

### S4. 記録は steps.jsonl に step=shadow_draft / shadow_review / shadow_verify として追記
- 既存の `_step` をそのまま使う。agent 名に影のエージェント名が入るので、どの影かは行で分かる。
- QueueItem には `shadow` フィールド（影のエージェント名、レビュー判定、警告数、失敗なら理由）だけ付ける。返信案本文はキューに出さない。
- 代替案: 別ファイル shadow.jsonl。却下理由: 「問い合わせ ID 1 つで全段が追える」を崩す。

### S5. 影の失敗は隔離
- 影の draft が失敗（fixture 欠落、構造不正）しても、既存経路の結果は変わらない。失敗は status=failed で記録され、QueueItem.shadow に理由が載る。

### S6. 比較は `shadow-report`
- 実行 1 回分について、問い合わせごとに「本番のレビュー判定と警告数 / 影のレビュー判定と警告数 / 影の失敗」を表にし、合計（pass の件数、警告の合計）を出す。昇格の判断材料。
- 代替案: 比較コマンドを作らず show --inquiry で見る。却下理由: 件数が増えると 1 件ずつ見るのは運用にならない。ただし実装は最小（表 1 枚）。

## Risks / Trade-offs

- [影の分だけ LLM 呼び出しが増える（draft とレビューで 2 回）] → 影は対象カテゴリだけに限る。
- [レビュー判定と警告数でも品質は測りきれない] → 人が show --inquiry で本文を見て最終判断する。採用率の仕組みは Open Question。
- [影のエージェントが本番の対応表に無い名前を指す] → 起動時に設定を検証し、未知の名前なら run を止める（記録し損ねるより止める）。

## Review（2026-11-09、実装後）

- 作者が 3 点を承認: shadow-report を設ける（人の側の能率を上げる方向）、影の候補は「確約を避け、確認事項を先に書く」人格（実モデルが INQ-001 で確約を書きレビューに flag された件への改善）、INQ-004 の影 fixture を意図的に欠落させて失敗の隔離を示す。

## Open Questions

- 影の返信案を人が「こちらの方が良い」と印を付ける仕組み（採用率）は要るか。v1 はレビュー判定と警告数のみ。
- UI を付ける段階（CLI の後）で、shadow-report を画面に出し、本番と影の返信案・判定を並べて見て、その場で昇格（対応表の書き換え）まで決められる動線にする。昇格の自動化はしないが、人の判断の手数は減らす。
