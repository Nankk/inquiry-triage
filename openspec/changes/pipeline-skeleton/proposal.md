## Why

顧客問い合わせの一次対応は「分類 → 担当者が規程と FAQ を調べて返信 → 上長が確認」の手作業で、分類と下書きに時間がかかる一方、誤った約束（返金・期日）を含む返信を送る事故は許されない。
LLM に全部やらせると「何を根拠に書いたか」「どこで間違えたか」が追えず、送信前の確認コストが下書きコストを上回る。

役割を分けた複数のエージェントと決定論的なオーケストレータで一次対応を自動化し、人が段落単位で承認してから送る仕組みをプロトタイプとして作る。

## What Changes

- 問い合わせを 1 件ずつ「分類 → 専門エージェントによる返信案 → 検査（LLM レビュー + 決定論的検証）→ 承認キュー」に流す一方向パイプラインを新設する。
- エージェントは 3 種類の役割（分類、専門担当 ×3、レビュー）。専門担当は分類結果で 1 つだけ選ばれ、レビューと決定論的検証は並列に走る。複数の問い合わせは並列に処理する。
- 各段の入出力を不変レコードとして実行ログに保存する。
- LLM の入出力を fixture として保存し、API キー無しで同じ結果を再現するリプレイモードを設ける。
- 人が承認キューを CLI で採用・却下・修正し、採用された返信だけが送信箱に出る。

## Non-goals

- メール・チャット等の実際の送受信連携
- 自己修正ループ（レビュー結果を専門エージェントに戻して書き直させること）
- 埋め込みによる FAQ 検索（v1 はカテゴリとキーワードの表引き）
- Web UI（v1 は CLI）

## Capabilities

### New Capabilities
- `inquiry-routing`: 分類エージェントが問い合わせをカテゴリ・緊急度に仕分け、専門エージェントを 1 つ選ぶ
- `reply-drafting`: 専門エージェントが FAQ 記事（決定論的に取得）を根拠に返信案を作る
- `reply-verification`: レビューエージェントと決定論的検証が返信案を検査し、警告を付ける
- `approval-queue`: 人が返信案を採用・却下・修正し、判断を記録する
- `run-record`: 各段の入出力を不変レコードとして保存し、再実行・監査できる
- `replay-mode`: LLM 呼び出しを fixture で置き換え、API キー無しで一周できる

### Modified Capabilities
（なし。新規プロジェクト）

## Impact

- 新規コード: `src/inquiry_triage/`（models, llm, agents, retrieval, verify, orchestrator, store, cli）
- 新規データ: `fixtures/`（架空の問い合わせ、FAQ、規程、リプレイ用 LLM 出力）
- 依存: 標準ライブラリのみ。ライブ実行時のみ `openai` クライアント（別 change）
