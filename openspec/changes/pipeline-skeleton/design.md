## Context

役割の異なる複数の LLM エージェントを組み合わせたときに、構成をどう切れば運用と保守に耐えるかを小さな題材で示す。
LLM に任せる部分を小さく、周囲の決定論的な仕組みと人の承認を大きく取る一方向パイプラインの設計パターンを、架空の題材（顧客問い合わせの一次対応）に当てる。
制約: 合計 6 時間程度。会社のコード・データは使わない。架空データのみ。

## Goals / Non-Goals

**Goals:**
- 役割の異なるエージェントが分業し、並列部分と直列部分が図で説明できる構成
- どのエージェントが何を根拠に何を出したかを、実行ログから 1 件ずつ追える
- API キーも網羅的な LLM 呼び出しも無しに、fixture だけでデモとテストが回る
- エージェントの追加・差し替えがファイル 1 つの追加で済む

**Non-Goals:**
- 返信品質の最適化（プロンプト調整）
- 実運用規模のスループット
- 送受信システムとの接続

## Decisions

### D1. オーケストレータはコード、エージェントは LLM
- 分岐（どの専門エージェントに渡すか）、並列化、再試行、記録はすべて Python コードで行う。LLM は「与えられた 1 つの仕事を構造化データで返す」だけ。
- 代替案: LLM をスーパーバイザにして他エージェントをツールとして呼ばせる（LangGraph 等の supervisor パターン）。却下理由: 分岐の根拠が追えず、同じ入力で同じ経路を通る保証がない。運用で「なぜこの担当に回ったか」を答えられない。

### D2. 自己修正ループを置かない
- レビューエージェントの指摘は専門エージェントに戻さず、警告として承認キューに付ける。直すのは人。
- 代替案: レビュー → 書き直し → 再レビューを N 回。却下理由: 収束の保証がなく、コストと遅延が読めない。間違いが「ループの中」に隠れ、人の目に届かない。

### D3. 根拠（FAQ 記事）の取得は決定論的
- 分類エージェントが返したカテゴリと、問い合わせ本文のキーワード一致で FAQ 記事を表引きし、専門エージェントには該当記事だけを渡す（文脈の物理削除）。
- 返信案は引用した記事 ID を構造化データで返し、決定論的検証が「存在する記事 ID か」を確認する。
- 代替案: 埋め込み類似検索。v1 では説明可能性を優先して見送り。拡張点として `Retriever` インターフェースに切る。

### D4. 検査は 2 系統を並列に
- LLM レビュー（文体・規程違反の疑い・顧客感情への配慮）と決定論的検証（引用 ID の存在、禁止表現、長さ、プレースホルダ残り）を並列に走らせ、両方の結果を承認キューに付ける。
- 決定論的に判定できるものは LLM に聞かない。LLM にしか判定できないものだけ LLM に聞く。

### D5. LLM 境界を 1 つのインターフェースに閉じ、リプレイを一級市民にする
- `LLMClient.complete(agent, key, prompt) -> dict`。実装は `ReplayClient`（fixture 読み）、`RecordingClient`（ライブ結果を fixture に保存）、`LiveClient`（OpenAI 互換 API）。
- fixture のキーは `<agent>/<inquiry_id>`。プロンプトのハッシュではなく業務キーにすることで、人が fixture を手で書ける・読める。
- テストは全て ReplayClient で走る。LLM 前後の決定論的処理（表引き、検証、記録、承認）を網羅する。

### D6. 構造化出力は境界で検証する
- 各エージェントの出力は dataclass に変換し、列挙値・必須項目を検証する。検証に失敗した出力はエージェントの失敗として記録し、その問い合わせだけを「人に回す」扱いにする。他の問い合わせの処理は止めない。

### D7. エージェントの追加は 1 ファイル
- 専門エージェントは `Agent` プロトコル（`name`, `run(ctx) -> output`）を満たすクラスで、カテゴリとの対応表に 1 行足せば分類先になる。
- 運用上の導入は「シャドーモード」で行う（v0.2）: 新しい専門エージェントの出力は記録されるがキューには出ず、既存の経路の結果と並べて人が比較する。一定件数で採用率が基準を超えたら有効化する。

### D8. 実行ログは追記専用 JSONL
- `runs/<run_id>/steps.jsonl` に段ごとの {step, agent, inquiry_id, input_ref, output, elapsed_ms, status} を追記。`decisions.jsonl` に人の判断を追記。後段が前段を書き換えない。
- 代替案: SQLite。v1 では grep と jq で読める JSONL を優先。

## Risks / Trade-offs

- [分類エージェントの誤分類] → 専門エージェントの出力に根拠記事が付かない・「分からない」が返り、決定論的検証で警告になる。承認キューで人が差し戻せる。
- [FAQ のキーワード表引きの取りこぼし] → 取りすぎ側に倒す（同カテゴリ全記事を候補にする上限付き）。拡張点として埋め込み検索を残す。
- [fixture と実 LLM 出力の乖離] → RecordingClient で実出力から fixture を作り直す運用手順を README に書く。
- [LLM レビューと決定論的検証の二重警告] → 両方キューに出す。重複は人にとってノイズだが、見落としよりは安い。

## Open Questions

- 緊急度 high の扱い（キューの先頭に出すだけか、別経路か）
