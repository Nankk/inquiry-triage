## Context

pipeline-skeleton の D7「エージェントの追加は 1 ファイル」と「導入はシャドーモードで」のうち、後者を実装する。
既存の経路（分類 → 表引き → 担当 → レビュー ∥ 検証 → キュー）には手を入れず、横に「記録だけの経路」を足す形にする。

## Decisions

### S1. 影にする単位は「カテゴリ → 影のエージェント名」の対応表
- 設定ファイル（JSON、標準ライブラリで読める）に `{"billing": "billing_specialist_v2"}` のように書く。1 行足せば影が走る。
- エージェントの定義（名前 → 人格）は agents.py の一覧に置き、本番の対応表と影の対応表はどちらもその一覧を参照する。昇格は本番の対応表の名前を書き換えるだけ。
- 代替案: CLI フラグ `--shadow billing=...`。却下理由: 運用で毎回打つものではなく、設定として残したい。
- 代替案: エージェント定義ごと設定ファイルに書く。却下理由: 人格文（プロンプト）はコードの一部としてレビューとテストの対象にしたい。

### S2. 影に渡す入力は既存と同じ
- 同じ問い合わせ、同じ候補記事（表引きは 1 回だけ）。比較が成り立つのは入力が同じときだけ。
- 影の fixture キーも `<影のエージェント名>/<inquiry_id>.json`。リプレイの仕組みはそのまま使える。

### S3. 影に付ける検査は決定論的検証のみ
- 引用の存在、禁止表現、長さ、プレースホルダ。LLM レビューは付けない（コスト倍増を避ける。v1 の Non-goal）。
- 比較指標は「警告数」。少ない方が良い、という単純なものから始める。

### S4. 記録は steps.jsonl に step=shadow_draft / shadow_verify として追記
- 既存の `_step` をそのまま使う。agent 名に影のエージェント名が入るので、どの影かは行で分かる。
- QueueItem には `shadow` フィールド（影のエージェント名と警告数、失敗なら理由）だけ付ける。返信案本文はキューに出さない。
- 代替案: 別ファイル shadow.jsonl。却下理由: 「問い合わせ ID 1 つで全段が追える」を崩す。

### S5. 影の失敗は隔離
- 影の draft が失敗（fixture 欠落、構造不正）しても、既存経路の結果は変わらない。失敗は status=failed で記録され、QueueItem.shadow に理由が載る。

### S6. 比較は `shadow-report`
- 実行 1 回分について、問い合わせごとに「本番の警告数 / 影の警告数 / 影の失敗」を表にし、合計を出す。昇格の判断材料。
- 代替案: 比較コマンドを作らず show --inquiry で見る。却下理由: 件数が増えると 1 件ずつ見るのは運用にならない。ただし実装は最小（表 1 枚）。

## Risks / Trade-offs

- [影の分だけ LLM 呼び出しが増える] → 影は対象カテゴリだけ、レビューは付けない。
- [警告数だけでは品質を測りきれない] → v1 の指標として割り切る。人が show --inquiry で本文を見て最終判断する。
- [影のエージェントが本番の対応表に無い名前を指す] → 起動時に設定を検証し、未知の名前なら run を止める（記録し損ねるより止める）。

## Open Questions

- 影の返信案を人が「こちらの方が良い」と印を付ける仕組み（採用率）は要るか。v1 は警告数のみ。
