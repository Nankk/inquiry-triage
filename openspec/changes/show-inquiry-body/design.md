## Context

キュー項目は「人が見る単位」（models.py QueueItem）だが、人が判断する材料のうち問い合わせ本文だけが入っていない。本文は inbox（fixtures/inbox.json）にあり、run の記録（steps.jsonl / queue.json）には写していない。

## Decisions

### B1. 本文は `QueueItem.body` として `queue.json` に写す
- enqueue 時に `Inquiry.body` をそのまま入れる。1 件あたり数百文字なので記録が肥大する心配はない。
- 代替案: API が `--inbox` のパスを覚えておき、要求のたびに inbox を読んで本文を補う。却下理由: run の記録が runs/ の外に依存する。inbox を差し替えたり消したりすると過去の run の本文が変わる・消えるのは、run-record の「後段が前段を書き換えない」と相容れない。
- 代替案: `steps.jsonl` の route 段の `input` に本文を入れる。却下理由: 各段の `input` は参照（ID と記事 ID）で統一しており、本文を 1 段だけ例外にすると読む側が段ごとに形を覚えることになる。キュー項目が「人が見る単位」なのだから、人が見るものはそこに置く。

### B2. 読む側は `body` の欠落を許す
- この change より前の run の `queue.json` には `body` が無い。API はそのまま返し（`dict(i)` を写すだけ）、画面と CLI は `None` のとき「本文なし（記録に含まれていません）」を出す。既存 run を書き換えない。

### B3. 置き場所は返信案の上、折りたたまない
- 承認キュー詳細: メタ情報（差出人・件名・緊急度・カテゴリ）の下、返信案の上に「問い合わせ」の区画。本文を読んでから返信案を読む順になる。
- 1 件の追跡: 「返信案の比較」の上に同じ区画。
- 代替案: 折りたたみ。却下理由: 本文を読まずに採用できる動線を作らない。長さは数百文字で、画面に収まる。

## Risks / Trade-offs

- [架空の問い合わせに顧客名が含まれる] → fixtures は架空データのみ（README に明記済み）。実データを扱うなら inbox の取り込み時点で扱いを決めるべきで、この change の範囲外。
