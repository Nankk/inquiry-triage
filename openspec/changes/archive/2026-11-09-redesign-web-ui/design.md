## Context

画面 3 枚（承認キュー、1 件の追跡、影の比較）は Vite + React + TypeScript、依存は react と react-dom のみ、業務ロジックは Python 側。見た目は `web/src/styles.css` 1 枚に CSS 変数で置いてあり、近黒の地に青 1 色、丸い札と角丸カード。PRODUCT.md（2026-11-10）に利用者（架空の一次対応担当者が主、構成を読む技術者（README とキャプチャの読者）が副）、UI 作業の制約（業務ロジックを持たせない、依存を足さない、キャプチャ再生成を維持）、用語を記録済み。

見た目の作り直しは Impeccable（`/impeccable`）の流れで進める。方向は乱数の割当（ロール）で決め、決定の記録はこの design.md、`.impeccable/surfaces/` の surface brief（方向の契約）、仕上げ時に生成する `DESIGN.md` と `.impeccable/design.json` に分かれる。

## Goals / Non-Goals

**Goals:**
- キャプチャ 1 枚で「段のある一方向の流れ」「本番と影の並走」「人の承認」が読めること
- 担当者が何十件も読む場面（日中の明るい事務所）で、本文・返信案・警告が今より読みやすいこと
- 操作の手数（一覧 → 詳細 → 採用・却下・修正）を増やさないこと
- 業務ツールに見えること。ランディングページやポートフォリオの見せ方にしない

**Non-Goals:**
- 機能・API・Python 側・hash の URL・依存の変更（proposal の Non-goals）
- 影の比較画面の表を図にすること

## Decisions

### D1. 世界は「鉄道の運行図表」。ロールの割当で決め、作者が決定ページで確定した

候補は日本の事務・窓口・公共の図版の伝統から 7 つ出し、共鳴の強い順に並べてから Impeccable の `concept-seed`（seed:edefc5bda0ac66a2、--scope direction --mode operate）を振った。型として最初から除いたのは、近黒の地に青 1 色の管理画面（現状）と、その裏返しの白地に灰の枠線・青ボタンの管理画面（標準の出口として別枠で提示）。

| 順 | 候補 | 機構の乗せ方 | 結果 |
|---|---|---|---|
| 1 | 複写伝票（多枚複写の業務伝票と検印欄） | 1 件 = 1 枚、複写の各葉 = 各段、検印欄 = 承認 | IMPECCABLE'S PICK として提示。帳票の世界は日本の業務ツールが最も落ちやすい着地点で、罫線が表の代用になると「書類の絵」になる危険を札に明記 |
| 2 | 稟議書・決裁回覧 | 決裁欄の判、付箋で未決 | 提示せず |
| 3 | 校正刷りと赤字 | レビューの指摘を欄外の朱書きに | 提示せず |
| 4 | 鉄道の運行図表と列車種別の色 | 1 件 = 1 本の列車、段 = 駅、本番 = 実線、影 = 破線、緊急度 = 種別色 | **ロールの割当。作者が選択** |
| 5 | 公共交通のサイン計画（路線色と駅番号） | カテゴリ = 路線色、ID = 駅番号 | 提示せず |
| 6 | 新聞の整理面 | 段組と見出しの階層で密度を捌く | 提示せず |
| 7 | 郵便（葉書・封書・消印・速達の赤線） | 1 件 = 1 通、速達の赤線 = 緊急 | 提示せず |

ロールが配ったカタログのチャレンジャー 6 つは、「利用者の自己同一化」と「製品の明瞭さ」の 2 軸で判定した。

- タブ付きマニュアル（rw-manual-acetate-tab-board）: 競合。殻にカテゴリ色の板を置く方向は Operate の規則の要請そのもので明瞭さで並ぶが、担当者の自己同一化で劣る。完全な代替として提示し、選ばれなかった
- 輝線のレール、星図、メトロのタイル、配信カタログの壁、カセットの J カード: 却下。暗い地、画像前提、手書きのいずれかで、「日中の明るい事務所で長時間」という確認済みの場面に反する。ただし各々から規律を 1 つずつ運行図表に足した: 状態は色でなく線の形で持つ（輝線のレール）、重要度は一本の固定目盛（星図）、返信案の長さ上限を目盛で見せる（J カード）、札に枠線を付けない（メトロ）、選択中だけ持ち上げ他を沈める（配信カタログ）

決定ページで作者が選んだ札は運行図表（THE ROLL）。スケッチは `.impeccable/mocks/decision/assigned.html`（1440×900、承認キューの画面を実データで組んだもの）で、実装はこの構図・配色・密度に合わせる。候補の全文は `.impeccable/mocks/decision/` と同じ時点の作業ノートにあり、この表がその要約。

### D2. 固定点（作者の指定。実装とレビューはこれを動かさない）

1. **段の横軸は等間隔に固定する。** 所要時間（elapsed_ms）は位置ではなく点の下の数字で添える。fixture リプレイでは各段が数ミリ秒で均一、実モデルでは担当の段だけ数秒になるので、時間を位置にすると両方のモードで読めなくなる。
2. **影の線（破線）は担当（shadow_draft）から始める。** 分類は本番と共通なので、影の線は分類には無い。
3. **方眼は殻（帯と一覧の背景）だけに敷く。** 本文・返信案・警告の面には敷かない。
4. **状態は色ではなく線の形で持つ。** 本番 = 実線、影 = 破線、失敗や「人が直接対応」= 線が止まって終端記号。色は緊急度の 3 色だけで、全画面で同じ。
5. **詳細の情報の順序は 本文 → 返信案（本番｜影）→ 警告 → 操作 を維持する。**
6. **hash の URL（#/queue/ID、#/inquiry/ID、#/shadow）は維持する。** 変えるなら scripts/screenshots.py も同じ change で直す。
7. **依存は足さない。** react と react-dom のみ、Python 側は触らない。画面に業務ロジックを持ち込まない。

実装前レビュー（2026-11-10）で足した固定点:

8. **失敗の扱いは実装に合わせる。** 線が止まって終端記号になるのは、その件が「返信案なし」でキューに載る場合（分類か担当の失敗、other）。レビューの失敗は本番の線を止めず、検査の駅に失敗の記号を付けて警告 1 行（「レビュー失敗」）に対応させる。影の失敗は破線だけがその駅で止まる。INQ-004 がその例（本番の線は続いて検査に失敗記号、影の破線は担当で止まる）。
9. **駅は 4 つ（分類・担当・検査・キュー）に統一する。** 駅は「LLM か人が関わり、失敗や警告が出うる点」に限る。FAQ 表引き（retrieve）はコードで失敗しないので駅にせず、担当の駅の注記（渡した記事 ID）に含める。
10. **追跡画面の steps.jsonl の行ごとの入出力ログ（JSON）は残す。** スジはその上に置く要約で、置き換えではない。「全段の記録」はこの製品の売り。

### D3. 字は OS のフォント族で、Web フォントは読み込まない

`"BIZ UDPGothic", "Hiragino Sans", "Noto Sans JP", "Yu Gothic UI", system-ui, sans-serif` の 1 族で見出し・本文・札・数字をまかなう（Operate 画面は 1 族で足りる）。数字は `font-variant-numeric: tabular-nums` で桁を揃える。

- 代替案: Google Fonts から BIZ UDPGothic を読み込む。却下理由: 実行時にネットワークへの依存が増え、「API キー無しで一周する」「screenshots.py が手元で撮り直せる」と相容れない。決定ページのスケッチだけは Google Fonts を使ったが、スケッチは出荷物ではない。
- 代替案: フォントファイルを `web/public/` に同梱する。却下理由: 日本語フォントはウェイト 1 つで数 MB になり、リポジトリと配信が重くなる。字形の差は OS ごとの代替で許容する。

### D4. スジは SVG を返す小さな部品 1 つにまとめる

`web/src/components/` に、段の並び（分類・担当・検査・キュー）と状態（本番／影の有無、失敗した段、人が直接対応）を受け取って SVG を返す部品を 1 つ置く。一覧の項目（小）と詳細・追跡画面（大、駅名と ms つき）は同じ部品の大きさ違い。段の並びと終端の導出は `lib.ts` の純粋関数にして vitest で確かめる。

- 代替案: CSS の擬似要素で線を描く。却下理由: 破線・終端記号・駅の点を揃えて描くには SVG の方が短く、拡大縮小も素直。

### D5. 殻はサイドバーをやめて上部の帯にする

一覧と詳細の左右は保つ。上部 56px の帯に 名前、承認キュー／影の比較のタブ、run 選択を置き、脚注（decisions.jsonl に追記されるだけ、昇格は次回の run から有効）は詳細の操作列の近くに移す。画面の横幅を一覧と詳細に使い切れる。

- 代替案: サイドバーを保ったまま色と部品だけ置き換える。構成の作り直しが本文・返信案・警告の読みやすさを損なうと判断したときの退避案。落とすときはその判断を design.md の Review 節に書く。

### D6. 色の戦略は Restrained。色は緊急度の 3 色だけ

地は紙白（#f7f6f2 付近）、墨（#1c2430 付近）が罫と文字、殻の方眼は薄い青灰。緊急度 高 = 赤（3px）、中 = 橙（2px）、低 = 墨（1.2px）を線の太さと色で、一覧・詳細・追跡画面で同じ目盛。pass／flag、採用／却下は塗りの濃淡と文字で分け、札に枠線は付けない。主ボタン（採用して送信箱へ）は墨の塗り。補助文字の灰は紙白の上で 4.5:1 以上を取る（決定ページのスケッチで検出フックが対比不足を出した点の修正）。

### D7. 記録の置き場

- 方向の契約（THESIS / OWN-WORLD / STORY / FIRST VIEWPORT / FORM / FINISH）: `.impeccable/surfaces/` の surface brief。実装とレビューの基準
- 設計システム（色・字・部品の決定）: 仕上げ時に Impeccable の documenter が `DESIGN.md` と `.impeccable/design.json` を生成する。生成後、ここからリンクする → [DESIGN.md](../../../../DESIGN.md)（生成前はリンク切れ）
- 仕上げレビュー: Impeccable の finish reviewer を 1 往復。ship / fix の判定と残った指摘はこの design.md の Review 節に写す

## Risks / Trade-offs

- [方眼が飾りになって読みにくい] → 殻だけに敷く（D2-3）。本文・返信案・警告は無地の白
- [等間隔の駅では「担当の段だけ遅い」が位置で読めない] → 点の下の ms の数字で読む（D2-1）。実モデルの記録（INQ-001）で確かめる
- [影の無い run、古い run（本文なし）、失敗した段の表示] → 影が無ければ破線を描かない。本文なしの表示は今のまま。失敗は D2-8 の規則で描き分ける
- [OS によって字形が変わる] → 1 族の代替順で許容（D3）。キャプチャは作者の環境で撮る
- [構成の作り直しが本文・返信案・警告の読みやすさを損なう] → D5 の代替案（サイドバー維持 + 見た目だけ）に落とす。判断を Review 節に書く
